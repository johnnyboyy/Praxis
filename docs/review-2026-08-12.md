## F1 — The planner is the entrance point, wired as an opt-in plugin

**Type:** architecture / inconsistency. **Disposition:** ticket.

The overview diagram draws the planner as the front door (`task → PLANNER (intake workflow)`).
The code wires it as an ordinary per-root contributor: `.praxis/config.json` →
`contributors.planner = planner_plugin:make`. If a root does not register it, the root has **no
`intake` workflow at all** — no path from a request to a plan.

The planner is also the lone **process-face** plugin: it ships phases + the `intake` workflow
(`planner_plugin.py:161,182`) and injects no judgment (`contribute()` returns `[]`,
`planner_plugin.py:219`). Every other bundled plugin (general/coding-stack/uiux/writing) is
judgment-face and genuinely optional. Making a core entrance capability opt-in the same way a
domain is opt-in is the inconsistency.

**Proposed resolution (recommended).** Promote `intake` into the core seed workflows alongside
`tdd-unit` / `rebuild-triple` (`workflow.py:97-130`) so the front door is always present. Let the
planner plugin keep **only** its judgment domains (`interviewing`, `planning`, `behavioral-spec`,
`spawn-integrity`). This splits "entrance point" (core) from "planning judgment" (plugin).

## F2 — Two plan-entry paths; the documented-primary one cascade-stalls here

**Type:** reliability / inconsistency. **Disposition:** ticket.

Two entry paths exist (`docs/design.md:209-223`):

- **ORCHESTRATOR** — `plan` tool → `conduct.run_tasklist_detached` → `cascade.launch_detached`
  double-forks a detached worker (`cascade.py:133`) that runs the whole DAG itself, spawning
  `claude -p` children per unit via `ClaudeExecutor` (`cascade.py:155`).
- **INLINE** — `register_plan` → `next_handoff` → `close_unit`, driven by the orchestrator.

The detached path's isolated `claude -p` children have been observed to **cascade-stall on this
repo** (operator note from a prior session; the workaround is to use `register_plan`). Meanwhile
the `orchestrate` skill and the overview diagram both describe the **inline** flow — the detached
ORCHESTRATOR path is not part of the real mental model. So the documented-primary path is the
unreliable, unused one.

**Suspected cause (unverified).** praxis-inside-praxis recursion, or the frame-gate / edit-gate
PreToolUse hooks blocking the detached child, or the child never receiving the MCP surface.

**Proposed resolution.** Either root-cause the detached child stall (reproduce, capture
`.praxis/cascade.log`) or **deprecate the detached path** in favor of the
orchestrator-drives-subagents model the skill already encodes.

## F4 — Naming: build-lap codenames and opaque acronyms as primary vocabulary

**Type:** naming / comprehension. **Disposition:** glossary (`docs/glossary.md`) + rename ticket.

**F4a — lap codenames leaked into durable artifacts.** `R2` / `R3a` / `R3b` appear ~39× across
`ARCHITECTURE.md`, `run.py`, `isolation.py` — and `R3` is even in the overview diagram. They name
components by *which build lap produced them*, not by what they do. Functional renames:

| codename | rename to | what it is |
|---|---|---|
| R2 | **adequacy barrier** | coverage (per-unit) + mutation (final), test-strength signal |
| R3a | **preservation gate** | coverage-diff / held-out at the rebuild seam |
| R3b | **rebuild isolation** | IR-only worktree + copy-detection tripwire + dep hygiene |

**F4b — opaque acronyms as primary nouns.** `IR` (the contract `extract` emits and `synthesize`
builds against — name it by what it provides) and `DAG` (the unit graph). Already-good functional
names to keep: *barrier, gate, phase, edge, workflow, frontier, tripwire, attractor, rebuild
triple*. Draft names in `docs/glossary.md`.

## F5 — Mutation testing is baked into the core as *the* barrier form

**Type:** architecture / layering. **Disposition:** ticket.

The overview diagram draws the FINAL BARRIER as "full suite + MUTATION signal", and the core
matches: `run.py` owns `mutation_verifier` (`:195`), `ts_mutation_verifier` (`:509`),
`adequacy_verifier`, and the final-barrier wiring (`:826-831`) assumes mutation. It is
command-*configurable* (no hard mutmut/Stryker dependency), but the *concept* "the barrier IS
mutation-at-threshold" lives in the engine.

The barrier concept is sound; what should move is **who defines the barrier's form.** A
well-set barrier's *how/what* should be scoped to the task, composed per-root — not universally
equated with mutation. The verifiers already fit the Contributor `verify` hook shape, so they can
move out of core.

**Proposed resolution.** Core keeps the *invariant* (a barrier exists; close is reachable only
through passed gates) and the *plumbing* (a `verify` hook runs at the barrier). The *form* —
mutation, coverage, held-out, or a task-specific signal — moves to a project- or plugin-supplied
adequacy contributor. Extends the existing `BACKLOG.md` "Mutation scope = plan blast radius" item
from **scope → ownership**.
